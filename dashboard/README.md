# React Security Dashboard

Owner: Member 6
Reviewer: Member 1

## Purpose

The dashboard provides a security-focused interface for the API-Sentinel system.

It will present runtime API security findings and operational status without exposing secrets, credentials, personal data, raw packet captures, or other sensitive evidence.

## Planned Views

### Endpoint Inventory

Display discovered API endpoints and their status, including:

- documented
- undocumented
- deprecated
- shadow API findings

### Alerts

Display security alerts generated by the API-Sentinel detection pipeline.

Alerts should support investigation without exposing sensitive request data.

### Triage

Provide security findings with enough information for investigation and remediation, including:

- affected endpoint
- finding type
- severity
- status
- relevant security context
- remediation state

### Evidence

Display masked and privacy-safe evidence associated with security findings.

Sensitive values such as:

- passwords
- bearer tokens
- cookies
- personal information
- private keys

must not be displayed or stored by the dashboard.

### OWASP Mapping

Security findings will be mapped to relevant OWASP API Security Top 10 categories where applicable.

### Performance and Health

Provide operational views for:

- request/event processing health
- latency measurements
- service/component health
- alert and detection status

## Security Requirements

The dashboard must:

1. Enforce authentication and authorization for protected views.
2. Prevent unauthorized users from accessing security evidence.
3. Avoid displaying secrets or sensitive personal information.
4. Use masked evidence for investigation views.
5. Handle malformed or unexpected API responses safely.
6. Avoid leaking sensitive information through UI errors or logs.
7. Include authorization tests for protected dashboard functionality.

## Testing

Dashboard changes should include relevant automated tests.

Tests should cover, where applicable:

- authorized access
- denied access
- malformed input
- API failure handling
- sensitive-data masking
- protected evidence access
- UI behaviour for security findings

## CI and Security Checks

The dashboard will participate in the project security pipeline.

Planned checks include:

- React linting
- React tests
- package/dependency audit
- secret scanning
- static analysis where applicable
- container scanning when the dashboard container is introduced
- SBOM generation as part of the release evidence

## Evidence

Changes should provide reproducible evidence where relevant, such as:

- test results
- security scan results
- screenshots
- measurements
- reproduction steps

Evidence must not contain real credentials, personal data, production information, raw packet captures, or sensitive logs.

## Known Limitations

The dashboard is currently in the foundation phase.

The backend API contracts, detection data, enforcement data, and authentication integration are being developed by other project components. Dashboard interfaces will therefore initially use controlled test fixtures until the required APIs are available.

## Ownership

Member 6 owns the dashboard implementation and dashboard-related tests.

Member 1 reviews security-sensitive dashboard changes.

Changes must follow the repository contribution and security policies.

## Data source (fixture vs live)

The dashboard renders bundled synthetic fixture data by default. The seam is
`src/dataSource.ts`, controlled by `VITE_DATA_SOURCE` (see `.env.example`):
`fixture` is the only wired source today; `live` is reserved for the
analytics management API and is deliberately labelled in the header as not
yet wired, so fixture numbers are never presented as live telemetry.

## Current implementation and verification

The current dashboard renders synthetic endpoint inventory, alerts/triage,
masked evidence, and fixture health/performance. Inventory, alert, evidence,
and health sections are labelled as fixtures; unavailable aggregate values are
shown as `Unavailable` or `Unmeasured`, not as zero or healthy. The OWASP API
Security Top 10 (2023) view reads `docs/owasp-api-security-mapping.json`
directly and displays each category's documented coverage and example result.
That mapping is a traceability aid, not an assessment or certification.

The alert view filters the synthetic fixture rows by severity and triage status,
shows the matching count, and reports when a filter has no matches. These are
local view filters only; the dashboard does not mutate triage status. Inventory
classification is explicitly unavailable in the fixture. The documented
management inventory contract supports `documented`, `method_not_documented`,
`path_not_documented`, and `visibility_unavailable`; it does not define a
deprecated classification.

Responsive tables use horizontal scrolling on narrow screens, and native
selects are keyboard accessible. Evidence is rendered from the bundled masked
fixture projection only. The dashboard has no management API client,
authentication/session integration, server-side RBAC, case scoping, or live
loading/error/empty response handling. The local alert filter has an empty
state; it is not a network response state. `sourceState.ts` documents supported
source states, while the app deliberately reports the management source as
unavailable.

The documented `MGT-LAB-1.0` read endpoints require a case-scoped reader Bearer
grant. The contract explicitly prohibits putting that credential in a Vite
bundle or browser storage, and there is no reviewed browser session bridge.
The dashboard therefore stays fixture-only; never treat client-side UI state
as an authorization boundary or infer live system health.

From the repository root, dashboard checks are:

```powershell
npm.cmd --prefix dashboard ci
npm.cmd --prefix dashboard run dev
npm.cmd --prefix dashboard run lint
npm.cmd --prefix dashboard test
npm.cmd --prefix dashboard run build
npm.cmd --prefix dashboard audit --audit-level=high
npm.cmd --prefix dashboard sbom --package-lock-only --sbom-format=cyclonedx
```

The `API-Sentinel CI` workflow runs the dashboard checks and the pinned Python
unittest suite. The separate Analytics Security Tests workflow also runs
repository tests and analytics-specific scans/evidence checks. A local pass
does not establish remote workflow success, branch protection, production
readiness, or release approval. The dashboard CI generates a CycloneDX SBOM
from the lockfile and retains it as a 30-day review artifact. The dashboard
container is built from `docker/Dockerfile.dashboard`; its image scan is
described below.

The dashboard workflow's dependency check is `npm audit --audit-level=high`;
it requires registry access. Repository security regression tests scan text
files for configured secret patterns and check sensitive-file exclusions. This
is a bounded repository check, not a claim of comprehensive secret detection.
CI validates the generated SBOM's CycloneDX format, 1.x specification version,
and non-empty component list before uploading the artifact.

The dashboard container is built from `docker/Dockerfile.dashboard`. The
`container-security` CI job scans that built image with Trivy for HIGH and
CRITICAL vulnerabilities and secrets, then uploads the JSON report for 30 days.
The scan currently records findings without failing the job
(`exit-code: '0'`); a passing job is therefore not proof that the image has no
findings. Review the report and record remediation or an explicitly accepted
risk before release.
